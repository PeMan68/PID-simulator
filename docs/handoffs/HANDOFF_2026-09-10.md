## 2. Produktvision

PID Simulator är en ren webbapp för undervisning och självstudier inom reglerteknik.

Appen ska främst stödja:
- lärarledda demonstrationer
- fler och snabbare experiment än fysiska laborationer medger
- självstudier genom lärstigar
- fördjupning inom reglerteknik
- träning i PID-tuning
- reglertekniska fenomen som är svåra att visa i fysisk labb

Simulatorn ska **inte** täcka hela kursens innehåll om mätdon och styrdon. Fokus är
regulatorn och reglerloopen:

```
process → mätdon → regulator → styrdon → process
```

Lärstigarna ska följa kursens veckoprogression och vara indelade i lämpliga
undervisningsportioner.

**Spelifiering är nu delvis genomförd** (se avsnitt 5/7) — en nivåprogression (badge,
nivånamn, grafisk mätare, inga synliga XP-tal) är aktiverad i produktion sedan v1.5.0.
Den mäter aktivitet/progression, är **inte ett betyg eller ett mått på
yrkeskompetens**, och sparas per webbläsare/enhet (inte per konto).

## 3. Gitflow och livscykel

```
feature/<uppdrags-id>-<kort-namn>  →  develop
bugfix/ÅÅÅÅ-NNN                    →  develop
release/<version>                  →  main  →  tillbaka till develop
hotfix/<version>-<kort-namn>       →  main  →  tillbaka till develop
```

Regler:
- Ett uppdrag per feature/bugfix-branch.
- Feature/bugfix-branches mergeas aldrig direkt till `main`.
- Direkta commits till `main` ska inte göras.
- `main` ska innehålla stabil undervisningsversion.
- `develop` ska innehålla fortsatt utveckling.
- Officiell GitHub Pages-URL publicerar uteslutande från `main`
  (`deploy-pid-simulator.yml`, triggar bara på push till `main`).
- Release till `main` sker endast efter PO/PM-beslut.
- **Ingen cherry-pick eller selektiv release används.** En release tar med hela `develop`.
- **Feature-/bugfix-brancher raderas lokalt OCH på origin** efter lyckad merge. Om en
  branch av misstag blir kvar lokalt utan att pushas (se avsnitt 14 för ett exempel som
  faktiskt hände), är den osynlig för andra maskiner tills den pushas.

Fyra statusnivåer — se `docs/development/ENVIRONMENTS.md` ("Livscykel"):
1. **Under utveckling** → `develop`.
2. **Tekniskt klar** — mergad till `develop`, syns i DEV, avstängd/dold i PROD.
3. **Produktionsgodkänd** — PO godkänner; läggs till i `catalog.prod.json`/`env.prod.js`.
4. **Publicerad** — via `release/<version>` till `main`.

> **Merge till `develop` betyder tekniskt klar. Aktivering i PROD betyder
> produktionsgodkänd. Publicering från `main` betyder releasad.**

## 14. Sessionsspecifik kontext

### Vad som INTE fanns i repot innan denna handoff skrevs

Till skillnad från tidigare handoffs (som kunnat skriva "allt är versionshanterat, inget
att överföra") fanns denna gång **en lokal, aldrig pushad branch**:
`feature/regulatortrimning` (FEAT-031, "Regulatortrimning i praktiken" — ett
övningsdokument, 2 commits ovanpå `develop`). Den existerade bara på den maskin där
detta uppdrag kördes och skulle ha varit **osynlig** för en annan dator som bara kör
`git pull`. Den är **pushad till origin som en del av denna handoff** (se
`git branch -r` — `origin/feature/regulatortrimning` ska nu finnas). Om du inte ser den
på origin, något gick fel med pushen och den behöver hämtas från den ursprungliga
maskinen.

**Lärdom för framtida sessioner:** en `git status --short --branch` visar bara
arbetskatalogens läge, INTE om andra lokala brancher saknar en fjärrmotsvarighet. Kör
`git branch -vv` för att se om någon lokal branch saknar `[origin/...]`-referens innan du
antar att allt är säkert överfört mellan maskiner.
